# Marketing and platform documentation

Establish the audience, channel, message, and release state. Ground claims in available release evidence and product behavior. Explain concrete user benefits without turning planned or unverified behavior into a promise.

Match the destination's supported format, requested voice, and length. The Nexus Mods and Bethesda Creations sections below apply only when the requested destination is one of those channels. They are not defaults for other tasks.

## Nexus Mods

Use only supported Nexus BBCode and preserve balanced tags, valid links, images, lists, emphasis, quotes, and code blocks. Do not invent tags or convert to Markdown unless requested. Check the actual page preview when available; balanced markup alone does not prove the page renders correctly.

## Bethesda Creations

Use only syntax known to work in the project's target restricted Markdown dialect. Do not assume full CommonMark or GitHub-Flavored Markdown support; use safe plain text when support is uncertain. Verify the destination preview when available and report unverified rendering separately.

## Preserve the content

When converting formats, preserve meaning, links, emphasis, lists, images, code, credits, and ordering where supported. Do not rewrite accurate wording merely to change markup. Report unsupported formatting and any unverified platform behavior.

Keep internal tracking, architecture, build machinery, and review artifacts out of public copy unless they help the audience make a meaningful decision. Prefer concrete feature descriptions and limitations to unsupported superlatives.

Check changed claims, links, assets, and markup. Inspect the destination preview when available and relevant; balanced markup does not prove rendering. Return finished copy with only the assumptions or limitations that affect publication. Preparing repository content does not authorize publishing it, sending messages, or changing external records.
